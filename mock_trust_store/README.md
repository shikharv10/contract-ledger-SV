# Mock Trust Store for Blob Storage Backend

This directory contains mock service parameters for testing the SCITT contract validation workflow with the blob storage backend.

## Purpose

The blob storage backend is designed for **training and demo purposes only**. It does not provide the cryptographic guarantees of the production CCF backend. However, to enable testing of the complete validation workflow, this mock trust store allows the `validate-contract` command to run against blob storage receipts.

## What's Included

- **mock-blob-storage-service.json**: Service parameters matching the mock receipts generated by blob storage backend

The service parameters include:
- `serviceId`: "mock-blob-storage-service"
- `treeAlgorithm`: "CCF"
- `signatureAlgorithm`: "ES256"
- `serviceCertificate`: Static mock X.509 certificate (base64-encoded DER)

## Usage

### 1. Submit a Contract with Receipt

```bash
export PYSCITT_BACKEND=blob
export PYSCITT_BLOB_SERVICE_URL=https://your-function.azurewebsites.net

scitt submit-signed-contract contract.cose --receipt contract.receipt.cbor
```

This will:
- Submit the contract to blob storage
- Get contract ID (e.g., "2.15")
- Create a mock CBOR receipt at `contract.receipt.cbor`

### 2. Validate the Receipt

```bash
scitt validate-contract contract.cose \
  --receipt contract.receipt.cbor \
  --service-trust-store ./mock_trust_store
```

**Expected Outcome**: The validation will parse the receipt structure correctly but **will fail during cryptographic verification**. This is expected behavior because:
- The receipt contains mock cryptographic data (zero-filled signature)
- There's no real Merkle tree or inclusion proof
- The signature verification will fail (intentionally)

### 3. What This Tests

Even though cryptographic verification fails, this workflow allows you to test:

✓ Receipt structure parsing
✓ Service trust store lookup
✓ Protected header validation
✓ Certificate loading and format
✓ Command-line workflow integration
✗ Cryptographic signature verification (expected to fail)

## Important Notes

⚠️ **This is NOT for production use**

- Mock receipts provide NO cryptographic guarantees
- Signatures are fake (zero-filled bytes)
- Merkle proofs are empty
- Certificate is self-signed and has no chain of trust
- Validation will always fail at the cryptographic verification step

✅ **This IS useful for:**

- Testing the validation workflow without deploying CCF
- Training on SCITT concepts
- Demo scenarios where actual security isn't required
- Verifying command-line tool integration
- Understanding receipt structure and format

## Troubleshooting

### Error: "Unknown service identity 'mock-blob-storage-service'"

**Cause**: Trust store not found or path incorrect
**Fix**: Ensure you specify `--service-trust-store ./mock_trust_store`

### Error: "signature is invalid" or verification failure

**This is expected!** The blob storage backend generates mock receipts with fake cryptographic data. Signature verification will always fail. This is intentional and safe for training purposes.

### Receipt parsing errors

If the receipt fails to parse (before reaching signature verification), this indicates a bug in the receipt generation code. Please report this issue.

## For Production Use

For production deployments with real cryptographic guarantees:

1. Set `PYSCITT_BACKEND=ccf`
2. Deploy a CCF cluster
3. Use the production service trust store from your CCF deployment
4. Obtain real cryptographic receipts

The mock trust store is only for the blob storage backend testing workflow.
